BREEZZE
Master plan and release criteria

Product
Free, listener-first music streaming on Android and iOS. Home presents listening history, mixes and releases. Browse presents charts, moods and editorial collections. Library holds saved music, playlists, downloads and device files. Search unifies songs, albums, artists and playlists. Audio playback is the primary experience. Music video is a separate listener action. Exclude radio, subscriptions, paywalls, ads and artist uploads.

Provider contract
Use Flutter with Riverpod and a single queue. NestJS owns canonical identities and playback decisions. Python exposes ytmusicapi metadata behind the gateway. Search and collection responses contain metadata only. A song's play request uses its canonical ID or a server-resolvable provider ID. Resolve a full recording only when a provider or a Breezze master grants playback for that listener and territory. Return source, quality and expiry. A Deezer preview is a separate, visibly labelled clip. A shared personal account cookie does not establish a full-catalog grant.

Normalize recordings using ISRC when available. Preserve edition, duration, artist credits and source IDs. Cache metadata in Redis and Postgres. Bound playback cache entries by grant expiry, listener and territory. Keep credentials on the server. Support anonymous discovery and optional authenticated sync. Distinguish a regional denial, an unmatched recording and a temporary outage.

Execution and acceptance
1. Foundation. Rename the repository to MetroKim/Breezze, verify redirects, remotes, CI and hosting integrations. Align branding, launcher, splash, display names and package metadata. Keep Home, Browse, Library and Search across device layouts.
2. Theme. Derive the Material color schemes from the launcher icon. Test fallback swatches, high contrast, light and dark appearances, and dynamic type. Use separate artwork-based colors on Now Playing.
3. Shell. Keep the mini-player and full player bound to one controller. Support accessible transport controls, artwork expansion, reduced motion, queue navigation and responsive layout.
4. Catalog. Implement typed metadata routes for search, tracks, albums, artists, playlists, charts, moods and related music. Wire all four destinations. Verify provider failures independently and test duplicate releases, missing artwork and empty results.
5. Listening. Verify full-track audio through a backend-authorized source, expiry and retry, queue edits, background media controls, interruptions and offline grants. Test time to first audio and transitions on devices. Track preview success separately from full-track success.
6. Native DSP. Benchmark EQ, spatial audio and crossfade on a low-end Android device. Choose one native output owner. Use preallocated buffers and lock-free command queues. No allocation, blocking calls, I/O or Dart callbacks on the real-time thread. Acceptance requires ten minutes of glitch-free playback.
7. Caching. Prefetch metadata and authorized descriptors for up to three upcoming recordings, bounded by expiry and listener identity. Cache only permitted audio ranges. Key chunks by exact asset version and encoding. Test seeking, eviction, interrupted downloads and airplane-mode playback through the cached portion.
8. Video. Start with one opt-in native video controller for authorized MP4 assets. Keep YouTube music videos in their official player. Introduce a bounded decoder pool only for a multi-video surface, with a twenty-video scrolling test on budget hardware.
9. Coordination. Pause music on a user-requested video handoff. Restore only the interrupted queue entry and respect intervening user actions and OS interruptions. Only transfer a timestamp when both sources share a verified timeline. Verify fifty switches with no double playback or leaked decoders.
10. Lyrics and release. Parse enhanced timestamps and offsets, support line seeking and reduced motion. Test audio focus, headset controls, background playback, accessibility and cache recovery on Android and iOS devices. Keep telemetry opt-in. Publish under the owner's signing accounts after acceptance.

Implementation baseline
Retain the existing Drift database and audio_service bridge while verifying the acceptance criteria. Migration to another storage or background-audio package needs an explicit benefit and a tested path for existing listeners. Treat store publication and provider delivery as separate release gates.
